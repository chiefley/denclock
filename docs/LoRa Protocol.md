# Den Clock and Weather — LoRa Protocol

## 1. Scope

This document defines the application-level packet protocol carried over the Den Clock and Weather LoRa network.

The LoRa/Wi-Fi gateway transports these packets between LoRa and MQTT. MQTT topics, MQTT encoding, retention, application storage, and other IP-side concerns are outside the scope of this protocol.

The first byte of every LoRa application packet is the **Message Class**. The Message Class determines the structure and interpretation of the remainder of the packet.

This document currently defines only the `SENSOR_REPORT` message class. Other message classes, including command and response traffic, will be specified separately.

---

## 2. General Protocol Principles

Different Message Classes may have different header structures. Fields required by one class are not required to appear in another merely to create a universal packet header.

The protocol does not contain a protocol-version field.

Message structures, field definitions, and TLV definitions are immutable once assigned. New capabilities are introduced through new Message Classes, new TLV Types, or other explicitly defined extensions rather than by changing the interpretation of existing wire representations.

All multibyte integer values are transmitted in **network byte order (big-endian)** unless a particular definition explicitly states otherwise.

---

## 3. SENSOR_REPORT

`SENSOR_REPORT` is an unsolicited report transmitted by a sensor node.

It is intended primarily for low-power nodes that spend most of their time asleep. A typical node wakes, measures its sensors, transmits one `SENSOR_REPORT`, and returns to sleep.

A `SENSOR_REPORT`:

- is unsolicited;
- identifies its source node;
- has no destination address;
- does not request or require a response;
- contains a sequence number;
- carries zero or more measurements encoded as TLVs.

The sensor does not need to maintain wall-clock time.

The LoRa/Wi-Fi gateway may associate a UTC reception timestamp, RSSI, SNR, and other radio or transport metadata with the received packet when forwarding it to MQTT. Such information is gateway metadata and is not part of the `SENSOR_REPORT` packet.

---

## 4. SENSOR_REPORT Packet Format

A `SENSOR_REPORT` consists of a four-byte fixed header followed immediately by zero or more TLVs.

```text
 Byte
   0          1           2          3          4 ...
+----------+----------+----------------------+------------------+
| Message  | Source   |      Sequence        |                  |
| Class    | Node ID  |       Number         |    TLVs ...      |
| 8 bits   | 8 bits   |       16 bits        |                  |
+----------+----------+----------------------+------------------+
```

Because the `SENSOR_REPORT` header has a fixed length, no header-length field or delimiter is required. The first TLV begins at byte 4.

### 4.1 Message Class

Size: **8 bits**

Identifies the packet as a `SENSOR_REPORT` and therefore determines the structure of the remainder of the packet.

The numeric Message Class value assigned to `SENSOR_REPORT` is TBD.

Message Class values are global to the LoRa application protocol.

### 4.2 Source Node ID

Size: **8 bits unsigned**

Identifies the physical LoRa node that originated the report.

Node IDs are assigned locally within the LoRa network.

The Node ID space is:

```text
0x00        Reserved / invalid
0x01–0xEF   Assignable node IDs
0xF0–0xFE   Reserved for future protocol use
0xFF        Reserved for broadcast
```

The broadcast value is reserved for possible future use. `SENSOR_REPORT` itself does not use destination addressing.

Friendly names such as `Porch Sensor` or `Attic Sensor` are application configuration and are not transmitted over LoRa.

### 4.3 Sequence Number

Size: **16 bits unsigned**

The Sequence Number identifies the order of reports generated by a sensor during one operating run.

Sequence Number **0** has special meaning:

> A Sequence Number of 0 identifies the first `SENSOR_REPORT` following sensor power-up or reset.

Subsequent reports use Sequence Numbers 1 through 65535.

After 65535, the sequence rolls over to **1**, not 0.

Therefore:

```text
Power-up/reset:

    0, 1, 2, 3, 4, ...

Normal rollover:

    ..., 65533, 65534, 65535, 1, 2, 3, ...
```

This allows a receiver to distinguish a sensor restart from normal sequence-number rollover.

A discontinuity between ordinary sequence numbers may indicate that one or more reports were not received.

For example:

```text
151, 152, 156
```

indicates that reports 153 through 155 may have been lost.

By contrast:

```text
151, 152, 0
```

indicates that the sensor restarted.

The Sequence Number is not a globally unique message identifier.

## 5. TLV Encoding

Measurements following the fixed header are encoded as **Type-Length-Value (TLV)** records.

```text
+----------+----------+-------------------------+
| Type     | Length   | Value                   |
| 8 bits   | 8 bits   | Length bytes            |
+----------+----------+-------------------------+
```

### 5.1 Type

Size: **8 bits**

Identifies the meaning and wire representation of the Value.

### 5.2 Length

Size: **8 bits unsigned**

Specifies the number of bytes contained in Value.

Length does not include the Type or Length bytes.

### 5.3 Value

Contains the value represented by the TLV Type.

The next TLV begins immediately after the final Value byte of the preceding TLV.

There is no TLV terminator. The TLV sequence ends at the end of the LoRa packet.

---

## 6. TLV Compatibility Rules

A TLV Type definition is immutable once assigned.

Its meaning, units, length, numeric representation, and scaling must not subsequently be changed.

If a different meaning or representation is required, a new TLV Type must be assigned.

A receiver that encounters an unknown Type must use its Length field to skip the Value and continue parsing subsequent TLVs.

TLVs may appear in any order unless a future Type definition explicitly states otherwise.

A particular measurement TLV should normally appear no more than once in a `SENSOR_REPORT`.

A packet is malformed if a TLV Length would cause its Value to extend beyond the end of the received packet. Parsing of that packet must stop at that point.

## 7. Initial Sensor TLVs

The initial sensor implementation reports:

- temperature;
- relative humidity;
- battery voltage.

Numeric Type assignments are TBD until the TLV Type registry is established.

### 7.1 TEMPERATURE

Value length: **2 bytes**

Representation: **signed 16-bit integer**

Units: **0.01 °C**

Examples:

```text
 2143 =  21.43 °C
    0 =   0.00 °C
-1250 = -12.50 °C
```

Temperature is always transmitted in Celsius. Conversion to Fahrenheit or other display units is an application responsibility.

### 7.2 RELATIVE_HUMIDITY

Value length: **2 bytes**

Representation: **unsigned 16-bit integer**

Units: **0.01 %RH**

Examples:

```text
 4321 =  43.21 %RH
10000 = 100.00 %RH
```

### 7.3 BATTERY_VOLTAGE

Value length: **2 bytes**

Representation: **unsigned 16-bit integer**

Units: **millivolts**

Examples:

```text
3912 = 3.912 V
4200 = 4.200 V
```

## 8. Illustrative SENSOR_REPORT

A sensor node might logically transmit:

```text
Message Class:       SENSOR_REPORT
Source Node ID:      12
Sequence Number:     3871

TLV:
    Type:             TEMPERATURE
    Length:           2
    Value:            2143
                      21.43 °C

TLV:
    Type:             RELATIVE_HUMIDITY
    Length:           2
    Value:            4321
                      43.21 %RH

TLV:
    Type:             BATTERY_VOLTAGE
    Length:           2
    Value:            3912
                      3.912 V
```

With three two-byte measurements, the complete application packet occupies 16 bytes:

```text
Fixed header                         4 bytes

Temperature TLV
    Type                             1
    Length                           1
    Value                            2

Relative humidity TLV
    Type                             1
    Length                           1
    Value                            2

Battery voltage TLV
    Type                             1
    Length                           1
    Value                            2
                                    --------
Total                               16 bytes
```

## 9. Extensibility

No protocol-version field is included in `SENSOR_REPORT`.

The fixed Message Class determines the header structure, and the fixed `SENSOR_REPORT` header determines where its TLV sequence begins.

Payload extensibility is provided by assigning new TLV Types while preserving all existing Type definitions.

For example, future sensor nodes could add TLVs for:

```text
Barometric pressure
Illuminance
Wind speed
Rainfall
Supply current
Internal sensor diagnostics
```

Existing receivers need not understand those Types. They can skip unknown TLVs using their Length fields while continuing to process Types they recognize.

Changes that would alter the interpretation or layout of the existing `SENSOR_REPORT` header must not be introduced by silently changing this specification.

---

## 10. Gateway Metadata

Information known by the gateway as a consequence of receiving a LoRa packet is not added to the LoRa packet itself.

Examples include:

- UTC reception timestamp;
- RSSI;
- SNR;
- gateway identity;
- radio parameters.

The gateway may attach such information when publishing the received packet to MQTT.

The gateway does not interpret sensor TLVs in order to perform this function.

---

## 11. Outside This Specification

The following are deliberately outside the `SENSOR_REPORT` wire protocol:

- MQTT topic structure;
- MQTT payload/envelope representation;
- MQTT QoS;
- MQTT retention or expiry;
- application persistence;
- historical data storage;
- browser presentation;
- DenClock display units;
- sensor reporting interval;
- LoRa radio parameters;
- command/response messages;
- command addressing;
- transaction identifiers;
- retries and acknowledgements;
- parser and serializer implementation architecture.

These concerns may be specified independently without changing the `SENSOR_REPORT` wire format.
